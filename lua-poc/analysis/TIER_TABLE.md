# Corpus Tier Table

Evidence for spec success-criterion 1 (Lua mapping-engine feasibility, Task 2).
Generated by `lua-poc/analysis/analyze_corpus.py` (Task 1) against the full
real mapping corpus available on this machine. Raw output committed as
`lua-poc/analysis/corpus-report.json` (all file versions) and
`lua-poc/analysis/corpus-report-canonical.json` (one representative per
logical mapping — see "Canonical (deduped) comparison" below).

**Headline numbers Task 3+ should cite are the canonical-only ones**
(T1 67.48% / T2 18.38% / T3 14.15%, 134 of 2,241 mappings T1-only): the
all-versions run counts every timestamped edit-history snapshot of a
mapping as a separate data point, which skews the sample toward whatever
organisations happen to re-save their mappings most often. Both are kept
here for transparency; the "Comparison against the zig-era baseline"
section below applies to the all-versions numbers only.

  the working directory of the local Delving SIP-Creator / PocketMapper
  install. Contains one subdirectory per organisation/environment
  (`brabantcloud`, `datahub`, `datahub_old`, `dcn`, `dcn-acpt`, `dcn-test`,

  `nk-dev`, `semafora`, `utralt`, ...), each with a `work/` directory of
  extracted `*.sip.zip` dataset directories. Each dataset directory holds
  the current `mapping_<prefix>.xml` plus timestamped snapshot copies
  (`<timestamp>__mapping_<prefix>.xml`) created every time the mapping was
  edited and re-saved — these are real historical versions of the same
  mapping, not synthetic duplicates.
- `sip-app/src/test/resources` — repo test fixtures (includes recorded
  `.sip.zip` mapped-output fixtures).
- `sip-core/src/test/resources` — repo test fixtures (per-format mapping

`find -L ~/PocketMapper -iname '*mapping*.xml'` matches 3,773 files; 3,560 of
those contain at least one parseable `<groovy-code>` snippet and are counted

`<groovy-code>` element — not investigated further, out of scope for this
task). Combined with the two repo test-resource roots (12 + 6 files), the

## Canonical (deduped) comparison — method

The PocketMapper corpus keeps a timestamped snapshot copy of a mapping
every time it's edited and re-saved (`<YYYY-MM-DDTHHMMSS>__mapping_<prefix>.xml`
alongside the live `mapping_<prefix>.xml`), so the all-versions run above
counts the same logical mapping design multiple times — once per point in
its edit history. `lua-poc/analysis/dedup_canonical.py` groups the corpus
into canonical mapping identities and reruns the same T1/T2/T3 analysis
(importing `analyze_corpus.py`'s `find_mapping_files`, `extract_snippets`,
and `analyze` directly, no logic duplicated) over one representative file
per group:

```
python3 lua-poc/analysis/dedup_canonical.py \
    ~/PocketMapper \
    sip-app/src/test/resources \
    sip-core/src/test/resources \
    -o lua-poc/analysis/corpus-report-canonical.json
```

- Grouping starts from the same 3,578-file population `analyze_corpus.py`
  actually analyzes (files with at least one extractable `<groovy-code>`
  snippet), not the raw 3,794-file glob — so every group is guaranteed a
  snippet-bearing representative and none get silently dropped.
- Canonical identity = (parent directory, filename with any leading
  `<YYYY-MM-DDTHHMMSS>__` prefix stripped). Filenames with a *different*
  prefix shape — e.g. the content-hash-prefixed fixtures seen under
  `sip-app/src/test/resources` (`FF9F5FE58279B40C9CB8251F5AEF657B__mapping_naa.xml`) —
  do **not** match the timestamp-prefix regex, so they are left as their
  own distinct canonical identity rather than merged.
- Representative per group: the bare (non-timestamped) file if one exists
  (the file the tool currently treats as "live"); otherwise the
  lexicographically last snapshot filename (same as chronologically latest,
  since the `YYYY-MM-DDTHHMMSS` format sorts as a string in date order).

Result: **3,578 snippet-bearing files → 2,241 canonical mappings, 84,698
snippets**. Output committed as `lua-poc/analysis/corpus-report-canonical.json`.

## Comparison against the zig-era baseline

The zig-prototype analysis (`zig-prototype/IMPLEMENTATION_STATUS.md` etc.)
cites **521 mapping files, 51,846 Groovy snippets**. This run found
**3,578 mapping files, 134,358 snippets** — same order of magnitude on
snippet count (2.6x), but 6.9x more mapping files. The discrepancy is
structural, not a corpus-size difference:

- `zig-prototype/groovy_feature_extractor.py` walked
  `<base>/<org>/PocketMapper/work*/<collection>/*mapping*.xml`, took only
  files directly in `<collection>/` (`xml_file.parent == collection_dir`),
  and explicitly **skipped any directory ending in `.sip.zip`**. That
  excludes both the timestamped snapshot copies and, in the current
  PocketMapper layout, the primary `mapping_*.xml` files themselves, which
  now live *inside* `<collection>.sip.zip/` directories.
- This run's analyzer (Task 1) does a flat recursive `*mapping*.xml` glob
  under `~/PocketMapper` with no `.sip.zip` exclusion and no "top-level
  file only" restriction, so it picks up every timestamped snapshot
  (1,360 of the 3,578 files matched have a `<timestamp>__mapping_*.xml`
  name) alongside the 2,218 canonically-named files.
- The zig-era run's `<base>/<org>/PocketMapper/work*/...` structure also
  does not match the current on-disk layout at all (`~/PocketMapper/<org>/work/...`,
  no nested `PocketMapper/` per org) — it was pointed at an older or
  differently-organized snapshot of the data, not the current
  `~/PocketMapper` install used here.

Net effect: this run's per-snippet tier percentages are computed over a
larger, version-inclusive sample (many snippets are near-duplicates across
timestamped edits of the same mapping), which is a reasonable and arguably
more representative corpus for this feasibility question, but it is not the
same population the zig-era 51,846 figure was drawn from. Treat the two
numbers as order-of-magnitude-comparable, not directly reconcilable.

# Golden-record capture cases

Ten real corpus mappings, selected per the Task 4 brief's tier quota (7×T1-only,
2×T2-max, 1×T3-max), captured against the production Groovy mapping engine.
Case layout consumed by `GoldenCapture` (Task 4), the verifier (Task 5), and
the Lua host (Task 8):

```
mappings/<name>/mapping.xml   rec-mapping XML (RecMapping.read)
mappings/<name>/recdef.xml    record-definition XML (RecDef.read)
mappings/<name>/record.xml    one <pocket id="...">...</pocket> fragment
```

`expected/<name>.rdf.xml` (generated by `make golden`) is the Groovy engine's
RDF/XML output for that record — the golden file a candidate Lua engine's
output gets diffed against.

## Selection

Source: `lua-poc/analysis/corpus-report-canonical.json`, `per_mapping[].max_tier`
over 2,241 canonical mappings (134 are T1-only). For each tier, mappings were
grouped by dataset directory basename (the same dataset is checked out
multiple times under different PocketMapper workspace roots — `lila/dcn`,
`lila/dcn2`, etc. — representing the same logical mapping; workspace copies
may differ in edit state, and the committed files here are the captured
source of truth; only the first occurrence per dataset name was kept) and
sorted by the size of the dataset's
smallest `source.xml.gz`/`*.xml.zst` sibling, ascending. The 7 smallest-source
T1-only, 2 smallest T2-max, and 1 smallest T3-max distinct datasets were
picked, all well under 15KB compressed — small enough to read and diff by eye.

For each case, the dataset's compressed source was decompressed and every
top-level `<pocket>` child of `<pockets>` was parsed with a real XML parser
(not a naive regex — see "record.xml extraction pitfall" below); the
most content-rich pocket among the first 100 was kept as `record.xml`,
verbatim except for whitespace trimming.

### `record.xml` extraction pitfall

The first extraction pass used a non-greedy regex (`<pocket\b[^>]*>.*?</pocket>`)
to pull one pocket out of the decompressed source. This broke on
`coll-schraven`/`collectie-schraven`: their source records are genuinely
double-wrapped — `<pocket id="X"><pocket id="X"><record id="X">...`
(a real artifact of the CSV→XML conversion, not a copy-paste error in this
harness) — so the non-greedy match stopped at the *inner* `</pocket>`,
producing an unbalanced fragment that `MetadataParser` rejected
(`Unexpected close tag </pockets>; expected </pocket>`). Fixed by parsing the
decompressed source with `xml.etree.ElementTree` and re-serializing each
top-level `<pocket>` element, which handles nesting correctly regardless of
depth. Lesson for Task 8 (or anyone touching source XML by hand): never slice
XML with regex when a real parser is one import away.

## Open question #1 (mapping-language-core.md §10): how does `_input['@id'][0]` resolve?

**Resolved empirically** by the first successful capture (`nationaal-gevangenismuseum`).

`sip-core/src/main/resources/MappingCategory.groovy:91-93` defines:

```groovy
static String getAt(GroovyNode node, Object what) {
    throw new UnsupportedOperationException();
}
```

...yet `CodeGenerator` unconditionally emits `_uniqueIdentifier = _input['@id'][0].toString()`
as boilerplate in every generated mapping
(`sip-core/src/main/java/eu/delving/metadata/CodeGenerator.java:263`, inside
`use (MappingCategory) { WORLD.input * { _input -> ... } }`), and every one of
the 10 captures above ran that line without throwing. The mechanism:

- `_input` inside the closure is a bare `GroovyNode` (the record root),
  supplied via `MappingCategory.multiply(List, Closure)` iterating
  `Collections.singletonList(rootNode)`.
- `_input['@id']` compiles to `getAt(_input, '@id')`. Two extension methods
  are in scope: the category's `getAt(GroovyNode, Object)` (the one that
  throws) and Groovy's own `DefaultGroovyMethods.getAt(Object, String)`
  (a one-line delegate to `InvokerHelper.getProperty(self, property)`).
  Because the actual argument is statically/dynamically a `String`, Groovy's
  overload resolution picks the **more specific** `String`-typed DGM overload
  over the category's `Object`-typed one — the category method is never
  invoked for string-keyed subscripts.
- `InvokerHelper.getProperty` then dispatches to `GroovyNode`'s own
  `getProperty` override, installed via a `DelegatingMetaClass` in
  `GroovyNode`'s static initializer (`sip-core/src/main/java/eu/delving/groovy/GroovyNode.java`,
  around lines 218-258), which resolves `'@id'` through `GroovyNode.get("@id")`
  and returns a one-element list — hence the trailing `[0]`.

**Consequence**: the `UnsupportedOperationException` guard in
`MappingCategory.getAt` is effectively dead code for `String`-keyed subscript
access on `GroovyNode` (the overwhelming common case, including the
boilerplate every single generated mapping depends on) — it would only ever
fire for a non-`String`, non-overridden-by-DGM key type, which no observed
generated code produces. A Lua port must replicate the **DGM/GroovyNode
`getProperty` path** (attribute/child lookup by name, wrapped in a list) for
`node[key]`, not the category's throw-on-everything behavior implied by
reading `MappingCategory.groovy` in isolation.

Verified independently (JSR-223 script under `EngineHolder`'s engine,
`use(MappingCategory) { n['@id'] }`) and by static analysis of `CodeGenerator`
+ `GroovyNode` + the decompiled `groovy-4.0.27.jar` DGM implementation; see
task-4-report.md for the full trace.
